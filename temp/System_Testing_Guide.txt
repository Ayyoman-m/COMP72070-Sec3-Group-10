1	Overview
Project IV focuses on System Level testing - this means looking at the complete system across all phases of the SDLC. You must complete Unit, Integration, Usability, and System testing for your project.
   The focus is on execution and traceability of the entire testing flow. This is a group deliverable - your team works together on test planning, test definitions, test execution, and logging.
Critical: Testing should happen continuously throughout the semester, NOT all at once at the end. The rubric specifically penalizes groups that do all testing at the last minute.
1.1	Why Does This Matter?
• System testing verifies the complete, integrated system fulfills its specified requirements
• It views the system from the customer and end-user perspective (end-to-end)
• Your SRS requirements drive what you test - if it's in the SRS, you must test it
• Traceability answers the question: "Are we done testing?"

3	Understanding Testing Levels
Your project requires testing at multiple levels. Here is what each means and how it applies to your project:
3.1	Unit/Functional Testing (Component Level)
• Tests individual functions, methods, or classes in isolation
• Uses MS Test framework in Visual Studio
• You have been doing this since Project I
• For your project: Test individual client functions and server functions separately
• Use Code Coverage to measure completeness (as practiced in Assignment #2)
3.2	Integration Testing
• Tests how modules and classes work together
• Verifies interfaces between components
• For your project: Test client-server communication, data packet serialization/deserialization, state machine transitions when triggered by actual commands
• Example: Does the client correctly send a LOGIN command AND does the server correctly process it and respond?
3.3	Usability Testing
• Tests from the user's perspective
• Based on your REQ-USE requirements from the SRS
• Does the UI make sense? Are buttons labeled clearly? Is feedback provided?
• For your project: Have someone unfamiliar with your app try to use it - can they figure out the workflow without help?
3.4	System Testing
• Tests the complete integrated system end-to-end
• Verifies the system fulfills ALL specified requirements
• Best performed in an environment similar to production
• For your project: Start the server, connect the client, authenticate, perform all operations, transfer large data, disconnect - does everything work together?

5.1	Source Control with GitHub

5.2	Bug/Defect Tracking with GitHub Issues
When a test fails, you must create a GitHub Issue:
1. Title: Clear summary of the defect
2. Description: What happened vs. what was expected
3. Steps to reproduce
4. Test case reference: Which test ID failed
5. Requirement reference: Which SRS requirement is affected
6. Severity/Priority
7. Screenshots or logs if applicable
   Reference the GitHub Issue number in your Test Log. When fixed, close the issue with a reference to the fixing commit. This provides traceability.

9	Tips for Exceeding Expectations
1. Start early - begin writing test definitions as soon as your SRS is done 2. Trace every test back to a requirement - this demonstrates thoroughness
3. Include negative tests - what happens when things go wrong?
4. Test state machine transitions exhaustively - valid AND invalid commands in each state
5. Keep your test log up to date weekly - don't batch it at the end
6. Use GitHub Issues properly - detailed bug reports show professionalism
7. Collaborate in MS Teams - the professor checks for collaboration evidence
8. Test at all levels - don't just do unit tests; include integration, system, and usability tests
10	Quick Reference - Testing Terminology
TermDefinitionVerification"Did we build the system right?" - checks against specificationsValidation"Did we build the right system?" - checks it solves the real problemStatic TestingExamining artifacts without execution (reviews, inspections)Dynamic TestingTesting by executing the softwareBlack-BoxTesting without knowledge of internal structureWhite-BoxTesting based on internal code structureTest CaseA specific set of inputs, preconditions, and expected resultsTest SuiteA collection of test casesDefect/BugA deviation from expected behaviorTraceabilityThe ability to link tests back to requirements and defectsCode CoverageThe percentage of code exercised by testsRegression TestingRe-running tests after changes to ensure nothing broke
A well-tested system is a well-understood system. Test early, test often, and trace everything.
